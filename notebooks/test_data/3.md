# IDoc, ALE, and EDI Operations Guide

> This document is synthetic SAP-related reference material created for testing ingestion, chunking, retrieval, and answer generation in a RAG system. It is written as realistic enterprise knowledge-base content, not as official SAP documentation.

## Overview

IDocs are structured intermediate documents used for asynchronous data exchange in SAP landscapes. ALE coordinates application-level distribution between SAP systems, while EDI commonly refers to business document exchange with external trading partners. IDocs are frequently used for orders, deliveries, invoices, material master data, customer master data, vendor master data, purchase orders, and shipment-related messages.

A RAG system supporting SAP operations should understand that an IDoc is not just a flat file. It has control records, data records, status records, message type, basic type, extension, partner profile, port configuration, process code, and application posting logic.

## IDoc Structure

### Control Record

The control record stores metadata about the IDoc. It includes sender, receiver, message type, basic type, extension, direction, partner information, and created timestamp. In SAP tables, control records are commonly associated with EDIDC.

### Data Records

Data records store segment data. A segment is a structured part of the message, such as header, item, address, schedule line, condition, or text segment. Data records are commonly associated with EDID4 in newer releases. Segment names are critical retrieval tokens because they explain mapping behavior.

### Status Records

Status records show lifecycle progress. They indicate whether the IDoc was created, passed to port, sent, received, processed, failed, or posted successfully. Status records are commonly associated with EDIDS. Operations teams often troubleshoot by checking the latest status code and its message.

## Common Transactions

- WE02: display IDocs by number, message type, status, date, partner, or direction.
- WE05: IDoc lists, similar operational display.
- WE19: test tool for copying and reprocessing IDocs.
- WE20: partner profile configuration.
- WE21: port configuration.
- BD87: reprocess inbound or outbound IDocs.
- BD64: distribution model maintenance for ALE.
- SM58: transactional RFC queue monitoring.
- SMQ1 and SMQ2: outbound and inbound qRFC queues.

For RAG ingestion, transaction codes should be preserved exactly because support analysts often search by T-code.

## Inbound IDoc Flow

1. External system or middleware sends an IDoc to SAP.
2. SAP receives the IDoc through a configured port and partner profile.
3. Control and data records are stored.
4. Inbound process code determines the function module or application handler.
5. Application logic validates fields, configuration, master data, and authorization.
6. Status records are updated.
7. If posting succeeds, a business document may be created.
8. If posting fails, the IDoc remains in an error status for correction or reprocessing.

Common inbound failures:

- Partner profile missing or incorrect.
- Message type not configured for partner.
- Process code points to wrong handler.
- Required segment field missing.
- Customer, vendor, material, plant, company code, or sales area not found.
- Duplicate external reference.
- Unit of measure mapping mismatch.
- Date format or currency format issue.
- Application document blocked by business validation.

## Outbound IDoc Flow

1. SAP application event occurs, such as purchase order output or material master change.
2. Output determination or change pointers trigger IDoc creation.
3. Partner profile determines outbound parameters.
4. IDoc is generated with control and data records.
5. Port configuration sends the message to middleware, file, tRFC, or another system.
6. Status is updated to show dispatch state.
7. Middleware transforms and sends the business document to the receiver.

Common outbound failures:

- Output condition record missing.
- Partner function is not maintained.
- Change pointer not active.
- Port destination unavailable.
- tRFC queue stuck in SM58.
- IDoc stays in status 30 because dispatch job is missing.
- Receiver rejects payload due to mapping validation.

## Message Types and Examples

Common IDoc message types include ORDERS for purchase orders or sales orders depending on context, INVOIC for invoices, DESADV for despatch advice, MATMAS for material master, DEBMAS for customer master, CREMAS for vendor master, DELVRY for delivery, and SHPMNT for shipment.

A query like "ORDERS IDoc failed status 51" should retrieve inbound posting failure content. A query like "MATMAS change pointer not generating IDoc" should retrieve outbound master data distribution and BDCP-related configuration.

## IDoc Status Interpretation

Status codes vary by direction and process, but common operational patterns include:

- Created but not yet dispatched.
- Passed to port successfully.
- Error in outbound processing.
- Inbound received but application posting failed.
- Inbound application document posted successfully.
- Technical communication failure.

Never treat status alone as root cause. The status message, application log, partner profile, process code, and business object must be inspected.

## Reprocessing Guidelines

Reprocessing is common but should not be careless. If the error is caused by missing master data or configuration, correct the root cause first, then reprocess. If the payload itself is wrong, changing SAP configuration may hide a sender defect. If the IDoc was already posted and retry creates duplicates, use business reference checks.

Safe reprocessing checklist:

1. Identify IDoc number, message type, direction, sender, receiver, status, and timestamp.
2. Read the latest status message and application log if available.
3. Confirm whether a business document was already created.
4. Identify whether correction is needed in payload, mapping, master data, configuration, or code.
5. Reprocess using BD87, WE19, or an approved job only after correction.
6. Record the outcome and cross-reference created document numbers.

## WE19 Testing Pattern

WE19 allows analysts or developers to copy an existing IDoc, edit segments, and test processing. It is useful for reproducing issues without waiting for the external sender. However, WE19 can create real business documents if executed in a productive client and should be used carefully.

Testing use cases:

- Verify whether a corrected segment value posts successfully.
- Compare two payload variants.
- Reproduce a mapping issue.
- Test a new IDoc extension.
- Trigger inbound function module in a controlled way.

## Partner Profile Design

WE20 partner profiles define inbound and outbound parameters. Configuration includes partner type, message type, process code, port, output mode, packet size, and permitted message flows. Partner profiles are often a source of hidden integration errors because one partner may be configured correctly in QA but not in production.

Design recommendations:

- Use clear naming conventions for partners and ports.
- Keep QA and production configurations aligned through transports where appropriate.
- Document process code mapping.
- Avoid mixing unrelated message types under poorly governed partner profiles.
- Include ownership information for each partner.

## IDoc Extensions

Standard IDoc types may not include all enterprise-specific fields. Extensions add custom segments. A custom extension must be coordinated across sender mapping, SAP segment definition, process logic, and receiver interpretation. If any layer is missing, the custom field may be ignored or cause errors.

RAG retrieval should connect extension names, custom segment names, BAdI or user exit logic, and middleware mapping documents.

## Observability and Correlation

Every integration should have correlation identifiers. For an IDoc, useful correlation data includes IDoc number, external document number, partner, message type, SAP document number, middleware message ID, timestamp, and status. If a helpdesk ticket says "supplier says we sent the invoice," the analyst needs a way to search by supplier invoice number, not only by IDoc number.
